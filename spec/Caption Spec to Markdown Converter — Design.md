# Caption Spec to Markdown Converter — Design

Nov 19, 2026 · @Baton Captions

## Overview

Build two separate Python tools and a web UI on top of them: `specconv` converts caption specs (PDF, HTML, DOCX, web pages) to Markdown, and `specval` independently checks each conversion against its source. The Markdown is a reference library used to look up the standard when solving issues, so fidelity matters more than looks.

**Approach (option A): best open-source tool per format.**

| Input | Tool | License |
| --- | --- | --- |
| HTML (local or fetched) | Pandoc | GPL-2.0 |
| DOCX | Pandoc | GPL-2.0 |
| Born-digital PDF | Docling (accurate table mode, no OCR) | MIT |
| JS-rendered web pages | Playwright (headless Chromium) for fetching only | Apache-2.0 |

**Goals**

- One command converts a folder of files plus a list of URLs into Markdown with YAML front matter.
- Outputs are deterministic for the same input and tool versions, so re-runs can be diffed.
- Every output keeps a copy of its source, so the validator and humans can compare.
- The validator runs on its own, on any conversion output, and produces a per-file report pointing to what a human must check.
- A web UI on the internal network lets anyone upload documents, follow progress, review reports, approve and download, using the same two tools underneath.

**Non-goals**

- No LLM rewriting of content. An optional formatting-only cleanup is out of scope for v1.
- No search UI, RAG indexing or chunk embedding. Section splitting is included so these can be added later.
- No cloud services or paid APIs, and no OCR: every input is a born-digital PDF, HTML or DOCX.

**Guiding principles**

1. Never alter tables, code blocks or values. Anything that must be exact is passed through as converted, never "fixed".
2. Prefer explicit structure. Convert HTML and DOCX directly; only PDFs go through layout reconstruction.
3. Fail loudly. A file that fails conversion is reported, never silently skipped.
4. Converter and validator share no conversion code, so a converter bug cannot hide itself in validation.
5. Open source only. Every tool, library and model weight must be under an open-source license that allows use inside a company. Check the license before adding any dependency; a tool with restricted weights (such as Marker) is excluded.

Two command-line tools in one repository, connected only through the output folder: `specconv` writes it, `specval` reads it.

## Inputs and fetching

Inputs come from two places: files in an input folder, and web pages listed in `sources.yaml`. Web pages are always downloaded first and converted from the saved HTML, never converted straight from the URL.

**Local files**

- Recursively scan `input/` for `.pdf`, `.html`, `.htm`, `.docx`. Ignore other extensions and log them as skipped.
- `.doc` (legacy Word) is not supported in v1; log it as `unsupported`.

**Web sources (`sources.yaml`)**

```yaml
sources:
  - id: ttml2
    url: https://www.w3.org/TR/ttml2/
    render: static        # static | browser
    clean: none           # none | main-content
  - id: vendor-caption-faq
    url: https://example.com/captions/faq
    render: browser       # page is built by JavaScript
    clean: main-content   # strip nav, header, footer
```

- `id` is required and unique; it names the output folder.
- `render: static` fetches with an HTTP client (httpx), following redirects, with a 30 s timeout and 3 retries.
- `render: browser` loads the page in Playwright Chromium, waits for network idle, then saves `page.content()`. Use it for JavaScript-built pages, including ReSpec editor's drafts.
- Fetched HTML is saved to `work/fetched/<id>.html` with a sidecar `<id>.fetch.json` holding URL, final URL after redirects, HTTP status, fetch time and render mode.
- `--refetch` forces a new download; otherwise a cached fetch is reused.

**HTML cleanup before conversion**

- `clean: none` (default, use for W3C and other spec pages): only remove `<script>`, `<style>`, `<noscript>`.
- `clean: main-content`: additionally remove `<nav>`, `<header>`, `<footer>`, `<aside>` and elements matching CSS selectors in an optional per-source `drop_selectors` list. If a `<main>` or `<article>` element exists, keep only it.
- Never use a boilerplate remover such as trafilatura; it can drop spec notes and tables.

**Edge cases to handle**

- Fetch failure or non-200 status: record in the run report and continue with other sources.
- Page that renders empty (under 500 characters of text after cleanup): flag as `suspect_empty` and suggest `render: browser`.
- Relative links and image URLs: rewrite to absolute using the final URL before conversion.

## Converter (`specconv`)

The converter routes each input to one converter, applies a small set of safe post-processing steps, and writes one output folder per document.

### Routing

| Input | Condition | Converter |
| --- | --- | --- |
| `.html`, `.htm`, fetched page | always | `PandocConverter` (from: html) |
| `.docx` | always | `PandocConverter` (from: docx) |
| `.pdf` | text layer on at least 70% of pages | `DoclingConverter` |
| `.pdf` | text layer on under 70% of pages | not converted; reported as `no_text_layer` so a damaged or image-only file never passes silently |

- A page "has a text layer" when pypdf extracts at least 50 non-whitespace characters from it. Both thresholds are config values.
- PDFs with text on some but not all pages are flagged `mixed_text_layer` in the manifest.

### Converter interface

```python
class Converter(Protocol):
    name: str
    def version(self) -> str: ...
    def convert(self, src: Path, out_dir: Path) -> ConversionResult: ...

@dataclass
class ConversionResult:
    markdown: str
    tool: str               # e.g. "docling"
    tool_version: str       # e.g. "2.120.2"
    options: dict           # exact options used, for the manifest
    media: list[Path]       # extracted images, relative to out_dir
    warnings: list[str]
    duration_s: float
```

Each converter lives in its own module. Adding a tool later means adding one class and one routing rule.

### Per-tool settings

**PandocConverter** (requires Pandoc 3.x on PATH)

```bash
pandoc SRC -f html -t gfm --wrap=none --extract-media=OUT/media -o OUT/raw.md
pandoc SRC -f docx --track-changes=accept -t gfm --wrap=none --extract-media=OUT/media -o OUT/raw.md
```

- `gfm` writes tables with merged cells as raw HTML; keep them as is.
- Keep heading `id` attributes where Pandoc emits them, so cross-references can resolve.
- Collect Pandoc stderr warnings into `warnings`.

**DoclingConverter**

- `PdfPipelineOptions`: `do_ocr=False`, `do_table_structure=True`, `table_structure_options.mode=TableFormerMode.ACCURATE`, `table_structure_options.do_cell_matching=True`.
- Images: export as referenced files in `media/` (image export mode `referenced`).
- Create the `DocumentConverter` once per run and reuse it; model loading is slow.
- Also save the Docling document as JSON to `work/<id>.docling.json` for debugging.

### Post-processing

Only these steps, in this order. Each step must leave fenced code blocks and tables byte-for-byte unchanged; implement them by first splitting the document into protected regions (fenced code, pipe tables, HTML `<table>` blocks) and other text.

1. Normalize line endings to LF and the file encoding to UTF-8.
2. Remove trailing whitespace on lines outside protected regions.
3. Collapse three or more blank lines to two outside protected regions.
4. Rewrite media links so they are relative to the document folder.
5. Prepend YAML front matter.

No other cleanup in v1: no heading repair, no paragraph joining, no LLM.

### Output layout

```text
output/
  manifest.json            # one entry per document, see below
  run-<timestamp>.log
  <id>/
    <id>.md                # the converted document
    source.<ext>           # exact copy of the input (or fetched HTML)
    media/                 # extracted images
    sections/              # only with --split
      index.md
      07-3-2-pop-on-captions.md
    conversion.json        # tool, version, options, warnings, timings
```

- `<id>` is the `sources.yaml` id for web pages, otherwise a slug of the file name. Duplicate slugs get a numeric suffix.
- `--split LEVEL` (default off) additionally writes one file per heading at that level into `sections/`, each with front matter naming its parent document and section number, plus an `index.md`. The full `<id>.md` is always written.

### Front matter

```yaml
---
id: cta-608-e
title: ""                   # filled by hand
spec_version: ""            # filled by hand
source_type: pdf            # pdf | html | docx | web
source_file: CTA-608-E.pdf
source_url: null            # set for web sources
source_sha256: 3f1c…
fetched_at: null            # set for web sources
converted_with: docling 2.120.2
converted_at: 2026-11-19T10:42:00Z
flags: []                   # e.g. mixed_text_layer
manual_fixes: []            # edited by hand
validated: null             # set by a person after review
---
```

On re-conversion, the fields `title`, `spec_version`, `manual_fixes` and `validated` are carried over from the existing file, and `validated` is reset to null if the Markdown body changed.

### Manifest

`output/manifest.json` lists every input with: id, source path or URL, route taken, converter and version, status (`ok`, `failed`, `no_text_layer`, `unsupported`, `skipped_unchanged`), flags, warnings and duration. The validator reads this file to find documents.

### Incremental runs

If the source SHA-256 and converter version match the previous manifest entry, skip the document and mark it `skipped_unchanged`. `--force` reconverts everything.

## Validator (`specval`)

The validator is a separate package that compares each converted Markdown file against its saved source and produces a report saying what passed and exactly what a person must check. It never edits document content.

### Independence rules

- `specval` must not import `specconv`. It reads only `output/manifest.json`, each `<id>/` folder and its own config.
- It extracts reference data from sources with different libraries than the converter uses: BeautifulSoup + lxml for HTML, python-docx for DOCX, pypdf and pdfplumber for PDF.
- It parses Markdown with markdown-it-py (pipe tables and fences as tokens), and BeautifulSoup for raw HTML tables inside the Markdown.

### Reference extraction

| Source | Text | Headings | Tables | Code blocks |
| --- | --- | --- | --- | --- |
| HTML | visible text after the same cleanup rules as the converter | `h1`–`h6` | `<table>` with rows, cols, cell text, spans | `<pre>` |
| DOCX | paragraph text in document order | `Heading N` styles | `w:tbl` with rows, cols, cell text | paragraphs in a code style or monospace font |
| PDF | pypdf text per page | not available | pdfplumber `find_tables`, marked approximate | not available |

### Checks

Each check returns `pass`, `warn`, `fail` or `not_applicable`, plus findings with location (Markdown line number, source page or element path) and a short excerpt.

| ID | Check | What it compares | Fail when (defaults, configurable) |
| --- | --- | --- | --- |
| V1 | Structure counts | Headings, tables, code blocks, images in source vs Markdown | Any count differs (HTML, DOCX); PDF table count differs by more than 1 from pdfplumber, else warn |
| V2 | Section numbering | Numbered headings such as `7.3.2` in reading order | A number is skipped, duplicated or out of order |
| V3 | Text completeness | Every source sentence present in Markdown text | Coverage under 98%; warn under 99.5% |
| V4 | Exact values | Multiset of protected tokens in source vs Markdown | Any token count differs |
| V5 | Table content | Cell-by-cell comparison | Any cell mismatch (HTML, DOCX); for PDF, see below |
| V6 | Code blocks | Code block text, XML well-formedness, WebVTT structure | Any mismatch or parse error |
| V7 | Markdown hygiene | Lint, heading level jumps, internal anchors, media links, front matter | Broken anchor, missing media, invalid front matter; lint issues warn only |
| V8 | Character confusion | Hex-like or numeric tokens containing `O`, `o`, `l`, `I`, `S` | Any hit in a table or code block; elsewhere warn |
| V9 | Acceptance questions | Expected answer snippets from `acceptance.yaml` | An expected snippet is missing from the named document |

**V3 text completeness details**

- Normalize both sides: Unicode NFKC, collapse whitespace, strip Markdown syntax from the output, join words hyphenated across PDF line breaks.
- Split the source into sentences; skip fragments under 20 characters (V4 covers short values).
- A sentence is `present` on an exact substring match, `near` when rapidfuzz `partial_ratio` is at least 95, otherwise `missing`. Report coverage as present plus near, and list every missing sentence with its page or element path.
- Compare by presence, not as a linear diff, because PDF extraction order can differ from Docling's reading order.

**V4 protected tokens (regex families, all configurable)**

- Hex values: `0x[0-9A-Fa-f]+`, `[0-9A-Fa-f]{2,4}h`, and 4-digit hex byte pairs inside tables (for example `9420`).
- Timecodes and timestamps: `HH:MM:SS:FF`, `HH:MM:SS;FF`, `HH:MM:SS.mmm`, `MM:SS.mmm`.
- Numbers with units: number followed by `px`, `%`, `rows`, `columns`, `fps`, `ms`, `s`, `c` (cells).
- Normative keywords, case-insensitive, whole words: shall, shall not, should, should not, may, must, must not, required, recommended, optional.
- XML names: namespaced names such as `tts:origin`, `ttp:frameRate`, `itts:fillLineGap`, and element tags.

For each family report source count, Markdown count, and up to 10 examples of tokens that appear more often on one side, with context.

**V5 table content details**

- HTML and DOCX: pair tables by order; if counts differ, pair by header-row similarity. Compare normalized cell text, honoring row and column spans. Report each mismatch as table number, row, column, source value, Markdown value.
- PDF: extract each table a second time with pdfplumber (MIT), an independent extractor, pair it with the Docling table by page and header similarity, and report every cell where they disagree. Agreement does not prove correctness but sharply narrows what to check.
- PDF tables pdfplumber cannot find: check that every Docling cell value appears in the text of the source page range; report cells not found.

**V6 code block details**

- HTML and DOCX: compare each code block to its source after normalizing line endings and trailing whitespace only.
- Any block that starts with `<` or is tagged `xml`, `ttml` or `html`: parse with lxml; report parse errors with line numbers.
- Any block that starts with `WEBVTT` or contains `-->`: check the header and every cue timing line against the WebVTT timing pattern.

### Review queue

For each document the validator builds an ordered list of things for a person to check:

1. Every `fail` finding.
2. Every table whose header or caption matches configurable patterns such as `code`, `character set`, `command`, `control`, even if it passed.
3. Every `warn` finding.
4. A random sample of source pages or sections (default 3, fixed seed so re-runs pick the same ones), to catch error types no check covers.

### Outputs

```text
validation/
  summary.csv              # one row per document: status per check, overall status
  <id>.json                # full machine-readable findings
  <id>.md                  # human report: results table, then the review queue
                           # with Markdown line numbers and source page numbers
```

Overall status per document: `fail` if any check fails, `warn` if any warns, else `pass`.

### Approval

`specval approve ID` is the only command that writes to a converted file. It sets `validated` in the front matter to today's date and the validator version, and only if the latest report has no `fail` findings or the person passes `--override` with a reason, which is recorded in `manual_fixes`.

### Acceptance questions file

```yaml
questions:
  - doc: cta-608-e
    question: Maximum rows in roll-up mode?
    expect: "4 rows"
  - doc: imsc-1-2
    question: Which attribute sets region position?
    expect: "tts:origin"
```

## Web application (`specweb`)

A third package, `specweb`, puts a browser UI on top of `specconv` and `specval` so anyone on the internal network can convert, review and download documents. It runs on one host with an open port and no login; it adds no conversion or validation logic of its own.

&#91;embedded content: web app architecture · one host, four parts\]

The web service only accepts uploads, stores files and shows results; all heavy work happens in the worker, so a slow conversion never blocks the UI.

### Users and access

- Anyone who can reach the port can use every feature. There are no accounts and no private jobs; the UI says so on the upload page.
- Each upload asks for an optional free-text name, stored on the job and on any approval, so reviews stay attributable.
- If access control is needed later, add HTTP basic auth or SSO in the reverse proxy (below); the app itself needs no change.

### Pages

| Page | What the user does |
| --- | --- |
| Upload | Drag in PDF, HTML or DOCX files and/or paste URLs (choose `static` or `browser` rendering per URL); optional split level; submit as one job |
| Jobs | See all jobs, newest first, with status and overall validation result; filter by status |
| Job detail | Per-document progress, then results; delete the job |
| Document | Tabs: rendered Markdown, raw Markdown, source preview side by side, validation report, review queue; download the `.md` or a zip with media; approve |
| Library | All approved documents with title, version, approval date and approver; download any of them |

**Document page details**

- Side-by-side view: Markdown on the left, source on the right. PDFs show in the browser's built-in viewer; HTML sources show in a sandboxed iframe with scripts disabled; DOCX sources are shown as Pandoc-rendered HTML preview plus a download link.
- Each review-queue item links to its Markdown line and source page, and has a checkbox. The Approve button is enabled once every `fail` item is ticked, or with an override reason, matching `specval approve`.
- Users may edit `title` and `spec_version` in a small form; these write to the front matter. The Markdown body is not editable in the UI in v1.

### API

The UI uses the same JSON API, so jobs can also be scripted.

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/api/jobs` | Multipart upload: files, `urls` (JSON list with render mode), options, submitter name |
| GET | `/api/jobs` | List jobs |
| GET | `/api/jobs/{job_id}` | Job status and its documents |
| DELETE | `/api/jobs/{job_id}` | Delete a job and its files |
| GET | `/api/documents/{doc_id}` | Metadata, front matter, validation summary |
| GET | `/api/documents/{doc_id}/markdown` | Raw Markdown |
| GET | `/api/documents/{doc_id}/source` | Original file |
| GET | `/api/documents/{doc_id}/report` | Validation JSON |
| GET | `/api/documents/{doc_id}/download.zip` | Markdown, media, report |
| POST | `/api/documents/{doc_id}/approve` | Approve, with name and optional override reason |
| PATCH | `/api/documents/{doc_id}/metadata` | Update `title`, `spec_version` |
| GET | `/healthz` | Liveness and dependency check |

### Jobs and workers

- Job states: `queued` → `fetching` → `converting` → `validating` → `done` or `error`. Each document within a job has its own state and result.
- Queue: Huey with its SQLite backend, so no extra service such as Redis is needed on a single host.
- Workers run in a separate process from the web server. Each worker loads the Docling models once and keeps them warm. Default concurrency is 1, configurable, because Docling uses several GB of memory per worker; size it on the real host in phase 8.
- Each job gets its own folder, laid out exactly as the CLIs expect, so the worker simply runs the `specconv` and `specval` Python entry points on it. This keeps one code path for CLI and UI.
- Every conversion step has a timeout (default 15 minutes per document) and runs in a subprocess, so a stuck or crashing converter cannot take down the worker.
- The browser polls job status every 2 seconds while a job is running; no websockets needed.

### Storage

```text
data/
  specweb.sqlite              # jobs, documents, approvals, queue
  jobs/<job_id>/
    input/                    # uploaded files and fetched pages
    output/                   # specconv output, same layout as the CLI
    validation/               # specval output
```

- Tables: `jobs` (id, created\_at, submitted\_by, status, options), `documents` (id, job\_id, source\_name, source\_type, status, converter, validation\_status, approved\_by, approved\_at, override\_reason).
- Approved documents are copied into `data/library/<doc_id>/` so deleting or expiring a job never removes an approved document.

### Security for an open internal port

No login means anyone on the network can submit work, so the app protects itself and the network:

- **Uploads:** maximum 100 MB per file and 20 files per job (configurable); allow only `.pdf`, `.html`, `.htm`, `.docx`, and check the file's actual type by its content, not just its extension; store under generated names, never the user's file name.
- **URL fetching (server-side request forgery):** the server fetches URLs on users' behalf, so by default block private, loopback and link-local addresses, and re-check after redirects. A config allowlist can permit specific internal hosts.
- **Rendering:** sanitize rendered Markdown HTML with nh3 before display, since converted tables can contain raw HTML. Show HTML sources only in a sandboxed iframe without scripts. Set a strict Content-Security-Policy.
- **Abuse limits:** cap queued jobs per client IP (default 5) and total queue length (default 50).
- **Transport:** run behind a reverse proxy (Caddy or nginx) that terminates HTTPS with an internal certificate.
- **Copyright reminder:** many standards are licensed documents, so the UI states that converted files are for internal reference only.

### Retention

- Jobs and their files are deleted automatically after 30 days (configurable) by a daily task; approved documents stay in the library.
- The Jobs page shows disk usage, and new jobs are refused with a clear message when free disk falls below a configurable threshold.

### UI technology

- Server-rendered pages with FastAPI, Jinja2 templates and HTMX for live updates. No JavaScript build step, so the app is simple to maintain.
- Markdown rendered server-side with markdown-it-py, then sanitized.
- Plain, accessible CSS; works in current Chrome, Edge and Firefox.

### Deployment

- Docker Compose with three services sharing one data volume: `web` (FastAPI via uvicorn), `worker` (Huey consumer with Docling, Pandoc and Chromium installed), `proxy` (Caddy).
- One image for `web` and `worker`, built from a Dockerfile that installs Pandoc 3.x and Playwright Chromium and pins all Python versions.
- Configuration through `specweb.yaml` plus environment variables for paths and port.
- Logs to stdout; `/healthz` used by Docker health checks.

## Configuration, CLI and build plan

Build in eleven phases, each ending with passing tests, so the converter is usable after phase 3 and the validator after phase 5, and the web app after phase 11.

### CLI

```bash
# converter
specconv fetch   --sources sources.yaml [--refetch] [--only ID]
specconv convert --input input/ --sources sources.yaml --output output/ \
                 [--split 2] [--force] [--only ID]

# validator
specval run     --output output/ [--doc ID] [--config specval.yaml]
specval approve ID --output output/ [--override "reason"]
```

- `convert` runs `fetch` automatically for sources not yet cached.
- Exit codes: 0 all ok; 1 at least one document failed; 2 bad configuration or missing system dependency.
- Use Typer for both CLIs and Python `logging`, with a log file per run.

### Configuration files

```yaml
# specconv.yaml
pdf:
  min_chars_per_page: 50
  min_text_page_ratio: 0.7
html:
  strip_tags: [script, style, noscript]
fetch:
  timeout_s: 30
  retries: 3
  user_agent: "specconv/1.0"
```

```yaml
# specval.yaml
text_coverage: {fail_below: 0.98, warn_below: 0.995, min_sentence_chars: 20, fuzzy_ratio: 95}
pdf_table_count_tolerance: 1
always_review_table_patterns: [code, "character set", command, control]
sample_pages: {count: 3, seed: 42}
token_families: {}   # optional extra regex families, merged with the defaults
```

### Dependencies

| Package | Needs |
| --- | --- |
| System | Python 3.11+, Pandoc 3.x, Chromium via `playwright install chromium`; for the web app: Docker with Compose |
| `specconv` | docling, pypdf, httpx, playwright, beautifulsoup4, lxml, pyyaml, typer |
| `specval` | pypdf, pdfplumber, python-docx, beautifulsoup4, lxml, markdown-it-py, rapidfuzz, pymarkdownlnt, pyyaml, typer |
| `specweb` | fastapi, uvicorn, jinja2, python-multipart, huey, sqlalchemy, markdown-it-py, nh3, filetype, pyyaml; HTMX served as a static file; Caddy as the proxy image |

Manage with uv and commit the lock file; these tools change weekly, so versions are always pinned. At startup, each CLI checks system dependencies and exits with code 2 and an install hint if any is missing.

### Testing

- **Fixtures, all synthetic** (never commit copyrighted specs): small HTML specs with numbered sections, a merged-cell code table, an XML example and a WebVTT example; the same content as DOCX generated with python-docx; and as PDF generated by printing the HTML with Playwright `page.pdf()`. One image-only PDF for routing tests.
- **Converter tests:** routing decisions, Pandoc and Docling outputs contain all fixture headings, tables and code blocks, post-processing leaves protected regions byte-identical, front matter carry-over on re-conversion, incremental skip.
- **Validator mutation tests (most important):** start from a known-good conversion, inject one defect at a time and assert the expected check fails and names the right location.

| Injected defect | Must fail |
| --- | --- |
| Delete a paragraph | V3 |
| Change `0x14` to `0x1A` | V4 |
| Change one "shall" to "should" | V4 |
| Remove a table row | V1 or V5 |
| Swap two cells in a table | V5 |
| Delete a closing XML tag in an example | V6 |
| Break a WebVTT timing line | V6 |
| Remove section 7.3.2 heading | V2 |
| Replace `0` with `O` in a hex value | V4, V8 |
| Point an image link at a missing file | V7 |

Also assert the unmodified conversion passes, so the checks do not produce false failures.

### Build phases

1. Repository skeleton, both packages, config loading, CLI stubs, manifest read and write, system dependency checks, and a `LICENSES.md` listing every dependency and model weight (including Docling's models) with its license.
2. `PandocConverter` for HTML and DOCX, post-processing with protected regions, front matter, output layout. Tests.
3. `DoclingConverter`, text-layer routing, `no_text_layer` reporting, incremental runs. Tests.
4. Fetching: `sources.yaml`, static and Playwright rendering, cleanup modes, fetch cache. Tests with a local HTTP server, no internet in tests.
5. Validator core: reference extraction, V1, V2, V4, V7, JSON and Markdown reports, `summary.csv`. Mutation tests for these.
6. Validator V3, V5 (including the pdfplumber table comparison for PDFs), V6, V8, V9, review queue, `approve`. Remaining mutation tests.
7. Optional extra: `--split`.
8. Run on three real specs (one PDF with code tables, one W3C page, one DOCX), review reports, tune thresholds. Write a README with setup and daily usage.
9. `specweb` core: FastAPI app, SQLite models, Huey queue, worker running `specconv` and `specval` per job folder, job API, Upload and Jobs pages. API tests with FastAPI's test client and a fake converter.
10. Document and Library pages: side-by-side view, report and review queue, metadata form, approve, downloads.
11. Hardening and deployment: upload checks, URL fetch protection, sanitizing, rate limits, retention task, disk check, Dockerfile, Compose file with Caddy, health checks. Tests for each protection, including blocked private-address URLs and redirects to them.

### Implementation rules

- Implement one phase at a time; run the full test suite before moving on, and stop for a design review if a phase needs a design change.
- Keep `specconv` and `specval` independent: no imports between them, no shared conversion code. A tiny shared `common` module for manifest schema and front matter parsing is allowed.
- `specweb` may call the `specconv` and `specval` entry points but must not copy or change their logic. Anything the UI needs that they lack is added to them first, with tests.
- Never add LLM calls, trafilatura or any step that rewrites content. Post-processing is limited to the five listed steps.
- Treat fenced code blocks and tables as immutable in every step after conversion.
- Use type hints throughout, dataclasses for results, and `pathlib`. No network access in tests.
- Pin all dependency versions and record tool versions in every manifest entry.
- When a threshold or regex choice is unclear, use the default in this design and list the question in the phase summary instead of guessing silently.
